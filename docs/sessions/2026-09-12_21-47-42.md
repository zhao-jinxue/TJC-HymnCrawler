# 修复歌词采集缺陷：副歌（lyrics_chorus）整段丢失

- 日期：2026-09-12
- 工具链：Cline
- 涉及模块：`crawler_core/extractor.py`、`crawler_core/db.py`、（拟新增）歌词 API 采集路径

## 任务 1：定位并修复歌词采集丢失副歌的缺陷

### 提问

1. 用户给出诗歌详情页 `https://sacredmusic.tjc.org.tw/hymn/12`（第 12 首〈耶穌尊名〉）。
2. 追问指出：DB 中 `verse_1` 只有 2 行，而网页上该节显示 4 行——网页 HTML 中同一节由
   两个 `div.lyrics_box` 组成（前者为节歌词，后者为副歌），说明「歌词的下载还存在缺陷，需要修复」。

### 解决思路

**根因定位**（用项目自带 Selenium 驱动导出真实 DOM）：

```text
hymn/12  tabs = [第1節, 第2節, 第3節, 第4節]
  tab[0] boxes=2 -> ['耶穌尊名入我耳中…', '美哉，大哉，耶穌我主！…']
  tab[1] boxes=2 -> ['耶穌尊名至高、至榮…', '美哉，大哉，耶穌我主！…']   ← 第 2 个 box 每节重复
  ...
```

`crawler_core/extractor.py` 的歌词循环中：

```python
boxes = driver.find_elements(By.CSS_SELECTOR, ".lyrics_box")
for box in boxes:
    text = box.text.strip()
    if text and text not in lyrics_parts:
        lyrics_parts.append(text)
        break        # ← 每个 Tab 只取第一个 box，副歌被丢弃
```

**影响面量化**（比对官网 JSON API `GET /api/hymn/{no}`，474 首逐首核对，脚本只读）：

| 项 | 数值 |
| --- | --- |
| 有副歌（`lyrics_chorus` 非空）的诗歌 | **270 首** |
| 其中副歌已进 DB 的 | **0 首**（100% 丢失，合计 559 行文本） |
| 节数一致 | 469 首 |
| 歌词错位/缺行 | 275（缺 16 行）、349（缺 4 行） |
| API 未取到（网络抖动，可重试） | 57 / 121 / 394 |

**可选方案**：

- A：DOM 方案——修正为收集每个 Tab 下全部 `.lyrics_box`，副歌并入每节末尾。
- B：API 方案——歌词改取 `GET /api/hymn/{no}` 的 `lyrics[]` + `lyrics_chorus`，正歌与副歌分别落库。

**选定方案（用户确认）**：方案 A/B 合并为「以官方 API 为权威源」——
歌词改取 `GET /api/hymn/{no}` 的 `lyrics[]`（正歌）与 `lyrics_chorus`（副歌），
正歌存入 `verse_1..10`，副歌新增 DB v6 字段 `chorus` 单独存放（与官网数据模型一致）；
同时保留 Selenium DOM 路径作为 API 不可用时的兜底，并修掉 `break` 缺陷。

`https://sacredmusic.tjc.org.tw/hymn/12` 现落库为：`verse_1` = 正歌 2 行、
`chorus` = 副歌 2 行（即网页上同一 Tab 的两个 `lyrics_box`），不再丢内容。

**遇到的困难**

- 站点证书链缺 Subject Key Identifier，Python 3.14 下 `requests` 默认校验失败 → 沿用项目既有做法
  `verify=False` + `# nosec B501`（与 `downloader.py` / `probe.py` 一致）。
- 服务端 HTML 里 `.lyrics_box` 是空占位（Vue 客户端渲染），直接 requests 抓 HTML 拿不到歌词 →
  改用官方 JSON API，并保留 Selenium DOM 兜底。
- bandit 要求 `# nosec` 与告警同一行，首版写在上一行导致仍是 High 告警，已修正。

**遗留问题**

- 本次仅重抓歌词；`title` / `lyricist` / `composer` / `source_info` 仍走 DOM，未与 API 的
  `lyricists` / `composers` / `history` / `youtube_urls` 字段对账（如需可另开任务）。
- 官网 API 存在偶发超时（首轮普查 3 首、本轮 0 首），已内置重试 + 失败复核一轮；
  如长期使用建议在 `verify` 中增加歌词一致性抽查。
- `chorus` 只在 `save_to_db`（Step 2）与 `lyrics_api` 中维护，导出类脚本（`tool/`）未涉及该字段。

## 会话总结

- 本次共处理 1 个任务（修复歌词副歌丢失缺陷）
- 关键收获：
  1. 「抓不到」的根因往往在 `break` 之类的提前退出——站点把一节歌词拆成多个同类元素，
     只取第一个就会静默丢内容，必须做全量元素归并 + 与官方 API 对账
  2. 只要站点存在结构化的官方 API（`/api/hymn/{no}`），优先用它取文本字段，
     比解析 SSR/CSR DOM 更稳、更快、更易校验
  3. 数据修复类任务应先做「全量影响面普查」再动手，避免只修个案
- 遗留事项：见上（元数据对账、verify 增加歌词抽查、`tool/` 导出脚本未含 `chorus`）
