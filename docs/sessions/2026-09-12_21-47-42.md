- 日期：2026-09-12
- 工具链：Cline

## 任务 1：定位并修复歌词采集丢失副歌的缺陷

### 提问

1. 用户给出诗歌详情页 `https://sacredmusic.tjc.org.tw/hymn/12`（第 12 首〈耶穌尊名〉）。
2. 追问指出：DB 中 `verse_1` 只有 2 行，而网页上该节显示 4 行——网页 HTML 中同一节由
   两个 `div.lyrics_box` 组成（前者为节歌词，后者为副歌），说明「歌词的下载还存在缺陷，需要修复」。

### 解决思路

**根因定位**（用项目自带 Selenium 驱动导出真实 DOM）：

```text
hymn/12  tabs = [第1節, 第2節, 第3節, 第4節]
  tab[0] boxes=2 -> ['耶穌尊名入我耳中…', '美哉，大哉，耶穌我主！…']
  tab[1] boxes=2 -> ['耶穌尊名至高、至榮…', '美哉，大哉，耶穌我主！…']   ← 第 2 个 box 每节重复
  ...
```

`crawler_core/extractor.py` 的歌词循环中：

```python
boxes = driver.find_elements(By.CSS_SELECTOR, ".lyrics_box")
for box in boxes:
    text = box.text.strip()
    if text and text not in lyrics_parts:
        lyrics_parts.append(text)
        break        # ← 每个 Tab 只取第一个 box，副歌被丢弃
```

**影响面量化**（比对官网 JSON API `GET /api/hymn/{no}`，474 首逐首核对，脚本只读）：

| 项 | 数值 |
| --- | --- |
| 有副歌（`lyrics_chorus` 非空）的诗歌 | **270 首** |
| 其中副歌已进 DB 的 | **0 首**（100% 丢失，合计 559 行文本） |
| 节数一致 | 469 首 |
| 歌词错位/缺行 | 275（缺 16 行）、349（缺 4 行） |
| API 未取到（网络抖动，可重试） | 57 / 121 / 394 |

**可选方案**：

- A：DOM 方案——修正为收集每个 Tab 下全部 `.lyrics_box`，副歌并入每节末尾。
- B：API 方案——歌词改取 `GET /api/hymn/{no}` 的 `lyrics[]` + `lyrics_chorus`，正歌与副歌分别落库。

**选定方案（用户确认）**：方案 A/B 合并为「以官方 API 为权威源」——
歌词改取 `GET /api/hymn/{no}` 的 `lyrics[]`（正歌）与 `lyrics_chorus`（副歌），
正歌存入 `verse_1..10`，副歌新增 DB v6 字段 `chorus` 单独存放（与官网数据模型一致）；
同时保留 Selenium DOM 路径作为 API 不可用时的兜底，并修掉 `break` 缺陷。

## 任务 2：评估「用官网 JSON API 重构、替代 Selenium」并输出设计文档

### 提问

- 用户：官网 JSON API 感觉更好用，是否可以用此方式**重构项目代码、替代 Selenium 的结构**，实现更快的爬虫效果？
- 追问（用户选择）：**先别动代码**，把完整重构方案写成设计文档，审阅后再决定。

### 解决思路

**方针：不做"感觉可行"的评估，全部结论用实测数据支撑；本轮只读、零代码改动。**

1. **摸清 Selenium 使用面**：全文检索确认只有 4 处使用——`driver.py`（定义）、`scanner.py`（列表翻页）、
   `extractor.py`（详情 + DOM 兜底）、`probe.py`（音频点击播放）；`downloader/images/checksums/verify` 下游均不用。
2. **摸清 API 全貌**：`/api/hymn/12` 已知；进一步发现 `/api/hymn` 是**分页列表接口**，
   且列表项字段 = 详情接口全字段（逐字段比对 5 首：值不同 0 个，仅详情多 `prev_no/next_no`）
   → **48 个请求（2.2 MB）即可拿全 474 首**，Step 1 与 Step 2 可合并。
3. **覆盖率对账（474 首逐首）**：PDF 与 `probe_report` **零差异**（直链 HEAD 200 `application/pdf`）；
   音频 API 474 首/1130 条 vs 现有 473 首/1120 条 → **API 反而多 11 首**（Selenium 点击式探测漏抓，
   如 122「彼此相愛」完全没抓到）；歌词/副歌与现状逐首 0 不一致。
4. **速度基准（同机实测）**：详情 2.27 s/首（Selenium）vs 0.212 s/首（API 10 线程）；
   列表 2.76 s/页 vs 0.61 s；音频探测从 8–10 min 降为 0；
   全链路由 **≈28–30 min → ≈2–3 min（≈10×）**。
5. **兼容性验证（决定"零迁移"能否成立）**：
   - API 顺序 == 现有 `seq` 序号：**474/474 一致**
   - 目录名 == `f"{seq:03d}_{sanitize(no+name)}"`：**473/474**（唯一例外 349，官网标题已改）
   - 文件名规则（`{no}_五线谱.pdf` / `{no}_{版本}版.{ext}`）：抽查全部命中
   - 音频版本名映射 = `API 分类名 + "版"`（与现有 1120 条文件名一致）
6. **风险识别**：内部接口非公开承诺（需字段自检 + DOM 降级）、限流（实测 16 线程 11 req/s 无 429，
   仍需并发上限 + 退避重试）、349 标题漂移（目录名以既有 `url_map.txt` 为准，绝不重命名）。

**纠错记录**：首轮"目录名可推导性"检查用了 `re.sub(r'[^0-9A-Za-z _-]','',…)`，
  会把中文全部剔除，导致校验退化为恒真（误报 474/474 通过）；改用与 `Scanner._create_dir`
  完全一致的 sanitize 规则后真实结果为 **473/474**（32 条差异实为标点被剔除，如「21美哉，主耶穌」）。

- 关键收获：
  1. 「抓不到」的根因往往在 `break` 之类的提前退出——站点把一节歌词拆成多个同类元素，
     只取第一个就会静默丢内容，必须做全量元素归并 + 与官方 API 对账
  2. 只要站点存在结构化的官方 API（`/api/hymn/{no}`），优先用它取文本字段，
     比解析 SSR/CSR DOM 更稳、更快、更易校验；本次进一步证实**列表接口即全量详情**，
     全量 474 首只需 48 个请求
  3. 数据修复类任务应先做「全量影响面普查」再动手，避免只修个案
  4. 重构类决策必须以**实测基准 + 逐首对账 + 兼容性验证**为前提（本次 10× 提速、11 首音频差异、
     473/474 目录名可推导等结论全部来自实测，而非推测）
  5. 写校验脚本时警惕"恒真式断言"：正则把中文剔除后 `x in y` 会静默退化为永远成立，
     必须用与生产代码一致的规则复算（本次已发现并纠正一处误判）
- 遗留事项：
  - 任务 1：元数据未与 API 对账、`verify` 未抽查歌词、`tool/` 导出脚本未含 `chorus`
