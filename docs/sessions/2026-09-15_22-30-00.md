## 任务 1：#334 / #349 的数据核查（对「重新下载」指令的实测校正）

### 提问
- 「#349 和 #334 可以考虑重新从网站下载，修改本地文件和数据库，反正有网站作为标准的数据来源」

### 解决思路
先按"网站是标准源"去核对**下载链路的元数据**（`data/probe_report.json`）与**本地文件**，再决定要不要重下：

1. 查 `probe_report.json`：474 条，`hymn_number` 是**诗歌编号**，`numbered_pdf` = `…/score/num/<编号>.pdf`
   （#349 例外，见下）。
2. 查本地目录命名：`Hymn_Downloads/<首位>_<第二位><标题>/<编号>_简谱.pdf`
   —— 与 `url_map.txt` 对照发现 **首位是网站列表序号、第二位才是诗歌编号**：
   `052_51_b萬古靈磐乙`、`334_329天父我神`、`339_334耶穌沙崙玫瑰`、`474_469靈恩大會`。
3. 关键发现：`pdf_jianpu.pdf_path()` 用**诗歌编号**去匹配**目录前缀**（`startswith("334_")`）
   → 命中 `334_329天父我神/329_简谱.pdf`（**另一首诗「天父我神」**）。
   `pdf_path(349)` 同理命中 `349_344暴風雨中的避難所/344_简谱.pdf`。
4. 量化影响：40 首抽样中 `pdf_path` 与正确文件**相同的只有 9 首**（都是编号 <52、序号恰等于编号的），
   其余 16 首（能同时取到新旧路径的）在旧逻辑下 **同构命中 0 处 / 学到 0 个码位**；
   修正后同一批样本 **命中 58 处 / 学到 19 个码位**。
   → 这正好解释了此前"40 首只命中 9 首"。
5. 逐首结论：
   - **#334**：本地文件没错，是**代码取错文件**（旧逻辑把「耶穌沙崙玫瑰」解析成「天父我神」）。
   - **#349**：文件与网站一致、`integrity_status=passed`，但该 PDF 与其它 473 份**不同源**：
     网站给的是 hash 形式的 `score/c463…b78.pdf`（非 `num/349.pdf`），
     实测尺寸 420×595（A5）、字体 `CrimsonText*`/`Type3`、**完全没有 `MMP2005` 简谱字体文本层**。
     渲染后目视确认内容正确（就是「奇妙的耶穌」，4 段词齐全）——即**格式不同源、需 OCR**，不是要重下。

### 最终结果
- **不重下**（网站侧文件与本地一致，问题不在文件）。
- 修 `pdf_jianpu.pdf_path()`：改为**按目录内文件名 `{编号}_简谱.pdf` 匹配**（+ 模块级索引缓存）；
  编号支持 `51_b` 这类带字母形式；索引口径见函数 docstring。
- 顺带修两条被本次取证暴露的判据缺陷：
  - `is_dot`：全宽横线（连音线/减时线，实测 `5e61`=0.93×0.111 / `5e63`=1.44×0.134）
    因高度 0.111 > `DOT_MAX_H`(0.10) 漏网 → 混进拍位形成"幽灵拍"；改用**宽度判据**（`WIDE_LINE_MIN_W=0.5`）。
  - `melody_rows`：小节线（`602d`，ih≈1.13）与贴边双纵线（ih≈1.15）各自成 y 层且元素数够多，
    被当成谱行 → 新增**线类层剔除**（层内超高元素占多数即剔除，`ROW_MAX_IH=1.0`）。
- 验证：`test/test_pdf_jianpu.py` 新增 4 个回归用例（错配目录 / `51_b` 文件名 / 全宽线 / 线类层）。
- 遗留：#349 需要走 OCR（`tool/qwen_ocr.py` 或 rapidocr）才能得到曲谱数据；本轮以
  `review_reason='未识别到谱层（元素数均 < 8）'` **显式记录**，不伪造、不错配。

## 任务 2：新建表保存「简谱曲谱 + 文本歌词 + 节拍（与歌词等长对应）」

### 提问
- 「既然已经论证可以执行，而且成功率很高，那就实施：数据库中创建新的表，保存简谱歌词，
  简谱曲谱➕文本歌词，节拍和歌词等长，对应得上」

### 解决思路
数据源取舍：**官方简谱 PDF**（网站标准源，矢量文本、每个音符/字都带坐标）为准；
PPT 侧（v8 `hymn_jianpu*`）降级为**旁证**（提供"码位 → 记号"学习样本）。

实测版式（#334 目视 + 坐标双证）：
- 一首 = 若干「乐句」= 2~4 个**谱层**（各声部，y 相差 ≈24pt，同页且 ≤40pt 归同组）+ 下方一「歌词块」；
- 歌词块 = 一谱多词的若干行（如 4 节，行距 ≈15pt，**每行字数相同**）；
- 谱层元素 x 呈拍位栅格（≈21pt），元素 = 音符字形 / 延长线 / 休止；
- **等长判据（用户要的"节拍和歌词等长"）**：主旋律层「去延长线后的元素数」== 每节歌词字数。
  实测 #334 乐句1：20 元素 − 4 延长 = 16 == 16 字（对照官方谱图 `3. 2 1 2 | 3 5 - | 6. 1 5 1 2 …` 逐字吻合）。

表设计（v9，5 张；不动 `tjc_hymn` 与 `hymn_jianpu*`）：
| 表 | 粒度 | 作用 |
| :--- | :--- | :--- |
| `hymn_score` | 每首一行 | PDF 路径 / 页数 / 乐句数 / 谱行数 / 拍数 / 字数 / 汇总校验 / 复核原因 |
| `hymn_score_line` | 每行谱一条 | `notes`（曲谱串）、`notes_core`（去延长线）、`code_seq`（无损码位）、拍数、音符数/字数/`count_delta` |
| `hymn_score_lyric` | 每节歌词一条 | `text` + 字数 + 是否与曲谱等长（一谱多词 → 多行） |
| `hymn_score_char` | 每个字一条 | 字 ↔ 记号 / 拍位 / Δ / `span`（2 = 一字多音） |
| `hymn_codepoint_map` | 每码位一条 | `MMP2005` 码位 → 记号（学一次可解码全部 474 首） |

### 最终结果
- 新增模块 `crawler_core/pdf_score.py`（PDF → 乐句 / 谱层 / 主旋律 / 歌词块 / 拍位 / 逐字对位 / 等长校验）
  与工具 `tool/build_score.py`（`--learn` / `--only` / `--limit` / `--dry-run` / `--stats` / `--show`）。
- DB **v9 五表**（`db.py`：DDL + `ensure_score_tables` + `save_score_records` + `load_score` +
  `load/save_codepoint_map` + `score_stats`），**不改动** `tjc_hymn` 与 v8 两表。
- 实测入库（474 首一轮 ≈18 秒、幂等可重跑；`--learn` 先学码位映射）：
  - `hymn_score` **473 首**（#349 因无文本层跳过并记录原因）
  - `hymn_score_line` **7914 行**（其中主旋律行 3316）
  - `hymn_score_lyric` **5481 行**（合计 **74525 字**）
  - `hymn_score_char` **27567 字**，逐字几何对位可靠 **27288（99.0%）**，一字多音（`span=2`）**220**
  - `hymn_codepoint_map` **27 个码位**（跨源学习）
- **「节拍和歌词等长、对应得上」落地为可查列**：
  `count_delta = note_count − syllable_count`（0 = 一字一音等长；>0 = 一字多音；<0 = 音符数不足需复核），
  配合 `beat_count`（拍位栅格）、`hymn_score_char.beat`（每个字的起拍）→ 逐字对位可用 SQL 直接验证。
- **记号归一化**：跨源学到的是 PPT 合成字形（`t` = 5 + 一条减时线），按 `简谱字体.ttf` 渲染对照
  （2026-09-15 目视确认）归一为简谱记号（`t` → `5-`、`a` → `1^---`）；`code_seq` 保留无损码位以备重解码。
- 验证：
  - pytest **全绿**（新增 `test/test_pdf_score.py` 15 项 + `test/test_pdf_jianpu.py` 4 项回归）
  - ruff / mypy / bandit **全绿**
  - 逐字对位抽样复核：#334 第 1 行 12 个字 Δ ≤ 1.1pt；第 7 字「在」落在**第 9 拍**
    （第 7~8 拍是延长线 → 正确地不配字）✓
- 困难与处理：
  1. `pdf_path` 错配 bug 的定位靠「目录名首位 = 网站序号 ≠ 编号」的命名规律 + 新旧路径命中率对比（0 vs 58 处）；
  2. 「无歌词块」的乐句（实测约占四成）起初被误报为「音符数与字数不等」→ 改为**只有本乐句有歌词时**才判等长，
     整首 `align_ok` 由 1 首提升到 **394 首**；
  3. 未解码码位**不**改判 `align_ok`（只影响记号可读性），避免"几何与等长"结论被解码进度绑架。

## 任务 3：把「曲谱 + 对应歌词」从库里读出来、对齐打印（`tool/show_score.py`）

### 提问
- 「`tjc_hymn.db`，看到了数据库的改动，如果我想输出简谱曲谱和曲谱匹配的歌词，应该怎么输出，
   例如在终端输出，怎么从数据库中读取数据，并组合，然后输出，写个程序，以诗歌 1 首和 14 首为示例」

### 解决思路
1. **先看库里现成的连接关系**（这决定"怎么组合"）：歌词挂在其**主旋律行**上 ——
   `hymn_score_line.line_no` ↔ `hymn_score_lyric.line_no`（一谱多词 → 多行）↔
   `hymn_score_char.line_no + char_no`（每字一行，带 `note_index` / `beat` / `delta`）。
   即：**组合关系在入库时就建好了，读端不需要重新对位**，只需按 `line_no` 分组 + 渲染。
2. **再定对齐口径**：`hymn_score_char.note_index` = 该字对应的元素在**行内元素序列中的序号**，
   于是谱行与词行可以共用同一套列位置：第 i 列 = 第 i 个谱元素（音符 / 延长线 `-` / 未解码 `?`）。
3. **踩到的坑（本次最有价值的发现）**：`notes` 字段是**拼接串**（`"".join(e.sym for e in elems)`），
   而一个元素可能是 2 个字符（PPT 合成字形 `t` → `5-`、升号 `#1`）→ **按字符数切分会整体错位**
   （实测 #14 乐句 1 的「王」被排到延长线 `-` 下面，而库里它明明是 `1`）。
   正确做法：元素边界取 `hymn_score_line.code_seq`（**空格分隔的逐元素码位**，`f"{cp:04x}"`），
   再用 `pdf_score.MANUAL_SEED` + 库内 `hymn_codepoint_map` 还原记号，并**同样过 `normalize_sym`**
   （否则库里存的 `t` 会直接印成 `t` 而不是 `5-`）。
4. 输出形态（人读优先）：按乐句分组，谱行在上、每节歌词在下（`词①②③…`），行尾给拍数/音符数/延长数/字数/Δ 与结论；
   逐字明细（`--chars`）给出「字(记号@拍位Δ偏差)`*`（`*` = 一字多音 span=2）」。
5. 工具只读库、不建表、不改数据；`--width` 可调列宽（按**东亚显示宽度**计算，汉字 = 2 列）。

### 最终结果
- 新增 `tool/show_score.py`：
  - `python tool/show_score.py 1 14`（本题示例）/ `1-14`（区间）/ `--db 路径`
  - `--chars` 逐字明细、`--all-parts` 连和声声部、`--width N`、`--list` 列出库内全部编号（含标题/校验）
- 示例输出（#1 乐句 1，节选）：
  ```
  谱 L1    │1  1  3  3  5  -  5  -  6  -  6  6  5  -  3  -│ 拍19 音符11 延长5 字11 Δ0 ✔ 一字一音等长
  词①      │聖 哉 聖 哉 聖    哉    全    能 大 主    宰│
  词②      │聖 哉 聖 哉 聖    哉    全    能 大 主    宰│
  词③      │聖 哉 聖 哉 聖    哉    全    能 大 主    宰│
  ```
- 顺手修掉的可读性/正确性问题：
  1. `Δ+0` → `Δ0`；无词乐句不再误标「✔ 一字一音等长」，改标
     「（无词乐句：间奏或第二段旋律，不参与等长判定）」，和声行标「和声声部，本身无词」；
  2. 「记号串 ≠ 入库 notes」时行内告警（用于发现映射来源漂移，本次即靠它抓出 `t`/`5-` 未归一化）；
  3. 未对位的字（`note_index = -1`）单列提示。
- 新增 `test/test_show_score.py`（10 项）：东亚宽度 / pad / **spread 中多字符记号只占一列**（旧 bug 的回归锚点，
  按**显示列**断言而非字符索引）/ `code_seq` 切分 / 未解码 → `?` / 合成字形归一 / `code_seq` 缺失时退化 /
  Δ 语义 / 区间解析 / 真实库自检（#1/#14：元素数 == 码位数、notes 串一致、`note_index` 在元素范围内、输出无错位告警）。
- 验证：`pytest` **171 passed**（161 + 10）；`ruff check .` 全绿；#1/#14 实跑输出如 README 示例。
- 遗留：`?`（未解码码位）仍限制可读性，与任务 2 同因（整行同构匹配受限）；#14 乐句 3 存在**真实** `Δ−1`
  （音符数不足），属作者记谱问题，工具已在行尾标 ❌ 供人工复核。

## 会话总结

- 本次共处理 3 个任务（数据核查 + v9 建表落地 + 人读输出工具）
- 关键收获：
  1. **「文件错」与「取错文件」必须用数据分开**：#334/#349 都表现为"解析不出来"，但 #334 是**代码错配**
     （已修），#349 是站点上传的**异版 PDF（无文本层）**。先比对「网站元数据 ↔ 本地文件 ↔ 解析结果」三层，
     再决定要不要重新下载——本轮因此**避免了无意义的重复下载**。
  2. **等长校验的语义要留足空间**：Δ>0（一字多音）与「无歌词可比」都不该判失败，只有 Δ<0（音符数不足）
     才是硬异常；语义定清楚后可用首数从 1 → 394。
  3. **判据要落到可查的列**：`count_delta` / `beat` / `span` / `review_reason` 让「节拍与歌词等长、逐字对应」
     可以一条 SQL 验证，而不是只存在于解析脚本的日志里。
  4. **串字段不能当结构用**：`notes` 是拼接串、`note_index` 是**元素序号**，两者单位不同（字符 vs 元素）；
     消费端必须用 `code_seq` 切元素边界，否则合成字形（`5-`）会让对齐整体错位一格。
     这类"字段语义与直觉不符"的坑，靠渲染层做一次自检（`"".join(elems) == notes`）就能立刻暴露。

- 遗留事项：
  1. #349 走 OCR（`tool/qwen_ocr.py`）或从 v8 PPT 侧补齐；
  2. 码位映射扩充（库学 27 个 + 人工种子 14 个，约四成行记号仍含 `?`）：瓶颈是「PPT 一行 4 小节 vs
     官方谱一行 6 小节」的**整行同构**匹配 → 下一步做**拍位级投票**（见 2026-09-15_21-09-00.md 任务 2）；
  3. 无词乐句（约四成）与 v8 / 五线谱交叉校验，确认是间奏还是「第二段旋律」；
  4. 本会话后期终端回显异常（命令实际已执行，输出需从重定向文件读取），不影响交付物。

## 任务 4：拍位级跨源学习（v9.1）——把「码位 → 记号」的 `?` 从 92.5% 压到 11.4%

### 提问

用户列出三条待办：`#349 走 OCR` / `拍位级投票` / `五线谱交叉校验`。本轮推进**拍位级投票**
（另两条本轮拿到关键结论，见下）。

### 解决思路

**第一步：先诊断，不猜**（三条数据就把方向定住了）

- **#349 的真文件是 `Hymn_Downloads/354_349奇妙的耶穌/349_简谱.pdf`**，不是 `349_344暴風雨中的避難所`
  —— 目录首位是**网站列表序号**（这正是之前修过的错配坑，我又差点踩回去）。该 PDF 里**没有
  MMP2005 字体**（只有 CrimsonText / TimesNewRoman）→ 谱面确实是图形绘制、无文本层 → **OCR 路线成立**，
  列入后续（PNG 已存在：`349_简谱.png`）。
- 未解码画像：库学 27 + 人工种子 14 = 40 种已解码；**44 种未解码 / 出现 39561 次 / 92.5% 的谱行含 `?`**。
  几何画像显示未解码里**绝大多数是音符类**（ih 0.39~0.50，与已知音符同尺度），只有 `602d`（ih 1.163）
  是小节线 → 值得投入，且**不能靠几何判音级**。

**第二步：先试「字形视觉比对」——否决，但换来一条关键认知**

- PDF 内嵌的 MMP2005 子集字体可以提取（`doc.extract_font`，cmap 110 个码位），能渲染成图、可做像素比对，
  一度看起来是最短路径。
- **留一验证只有 10%**：隐藏一个已知码位，与其余已知字形做（保持纵横比的归一化位图 IoU × 宽高比）比对，
  最相似者往往**不是**同一音级（`5`↔`6` 0.61、`1`↔`h` 0.7 这类）→ **像素相似度无法区分语义**。
- 顺手做一个盲测检验我自己的目视能力（40 个已知码位、只标序号的字形图）：`MANUAL_SEED` 那 14 个
  "干净数字" **14/14 全对**，但**带八度点/减时线的变体判不对**（把 `h`=`5^---` 看成 6、`d`=`2^---` 看成 1）
  → **目视只能当旁证，不能当主证据**。
- 于是结论明确：`码位 → 记号`的**语义真值只能来自"人做的 PPT 记号"** → 回到跨源对齐，也就是拍位级投票。

**第三步：拍位级锚点投票（三轮试错才站住）**

1. `v2 扩展版`：两侧降为**音级序列**（`1`..`7`/`0`，变体字形按音级归并），`difflib` 求最长公共连续段当锚点，
   再向两侧逐位扩展投票 → **留一验证仅 24%**：盲目扩展会错位（`4e47` 被投成 `1`、`4e45` 被投成 `5`）。
2. `v3 夹逼版`：只投「两个锚点夹出的等长区间」→ 逻辑干净，但**覆盖率崩了**（命中行对 78、只有 9 个码位有票）。
3. **停下来量化瓶颈**：打印「PDF 谱行 × PPT 记号行」的**锚点覆盖率矩阵**，结果一目了然
   —— **真对应 0.82~1.0（#334 首行 `32123565123` ↔ PDF `3212356512321234` = 1.0），假对应 ≤0.6（多为 0）**。
   也就是说：瓶颈不是"怎么投票"，而是"**哪对行才是同一句**"。
4. `v5 最终版`：**覆盖率闸门 `cov_min=0.6`** + 只在「锚点 ↔ 相邻锚点」与「锚点 ↔ 该侧下一个**已知**音级」
   的**等长区间**投票，后者自带**端点验证**（按 1:1 算出 PPT 侧对应位置，对得上才认这段）→ 实测
   「宁缺勿错」：`#1` 乐句 2 有个 `?`，PPT 那行少记了一个音（端点对不上）→ 自动作废、不猜。
5. **多轮自举**（`rounds`，默认 3）：一轮学到的音级下一轮就是新锚点，滚动扩增（单轮只有十几个码位有票）。
6. **参数调优（用实测数据否决了"放宽阈值"）**：`min_len` 2/3、`pair_min` 2/3/4、`cov_min` 0.5/0.55/0.6 各档跑遍，
   放宽只多解 1 种码位，而 `4e5e` 的票占比从 42% 掉到 34%（越放宽越散）→ **维持默认**（有据可依的取舍）。

**第四步：收尾走查又抓出三个真实缺陷**（都写进代码注释，避免重犯）

1. **未解码的"修饰"会被误当音符投票**：新学映射里 `5d27` 被投成了音级 `5`，但把它放大到 170px 目视，
   它是**降号 b**（墨迹 0.246×0.115，与升号 `5d26` 同族）。根因：PPT 侧升降号是零宽叠加字符
   （`ppt_symbols` 剔除），PDF 侧却是**独立字符** → 两侧位置错开。修法：`learn_elements` 增加几何闸门
   ——**未解码**且「又矮又窄（ih<0.30 且 iw<0.16）」判为修饰，不参与比对（必须只对"未解码"生效：
   已解码的紧贴元素是真实拍位）。
2. **同一票被重复计数**：区间、左右端点验证三条路径会覆盖同一位置 → `(3,'4')` 被记 3 次，等于偷偷给
   单次证据加权。修法：`votes_from_pair` 内部去重（同时不影响"多条独立路径一致"的加权语义）。
3. **幂等清理顺序错了会"越跑越少"**：把"清掉上一轮 `source=anchored`"放在学习**之后** → 学习时锚点仍含
   上一轮的 20 条（所以"新学"只有 1 条），清完只剩这 1 条 → 覆盖率从 25.9% **回退**到 92.5%。
   修法：**先清后学**（顺序与原因写进注释）。

**第五步：用字形图反向补种子（能确定的才补）**

把提取出的 MMP2005 子集字体放大到 170px 目视：`5d4c` 是**休止符 `0`**（PPT 侧 `0` 被当零宽叠加字符剔除，
跨源永远没有票）、`4e3c`=5、`5d42`/`4e42`/`4ed9`=7、`4e43`=6、`5d27`=降号 → 补进 `MANUAL_SEED`
（附"依据 + 为何跨源学不到"的注释）。**看不准的一律不补**：`4e5e`（字形像 `i`，出现 2009 次）先用
"最近锚点投影"收集证据——投影到的 PPT 记号**极度分散**（5/7/6/5-/1^-…）→ 它根本不是"与 PPT 记号
一一对应的音符"，**继续显示 `?`** 才是诚实的。

**顺带查清的两件事（用户另两条待办的结论）**

- **#349**：真文件（`354_349奇妙的耶穌/349_简谱.pdf`）里没有 MMP2005 字体 → 谱面是图形 →
  **确定需要 OCR**；PNG 已就位（`349_简谱.png`），本轮不动。
- **五线谱交叉校验**：五线谱 PDF **同样有文本层**，内容是 Finale/Sibelius 风格的音符字形编码
  （`ˆ_«««««ˆ`、`œ_»»»ˆ_««««`）**外加完整歌词**（`1.聖 2.聖 3.聖 哉，…`）。结论：这条路线**可行**，
  但要逆向那套音符字形编码才能取拍数/音符数；另有更轻的用法——只用它的歌词行做「音节数」交叉校验。
  记为后续。
