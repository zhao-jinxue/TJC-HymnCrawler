## 任务 1：给 tjc_hymn 增加音频时长字段并写入数据

### 提问
> tjc_hymn.db 数据库的 tjc_hymn 表中，再增加一个字段，写入每个音频的时长，参考 audio_versions 和
> audio_version_list 两个字段，一一匹配的结构，因此需要调整数据库的创建，调整 tjc_hymn.db 数据库的字段顺序，
> 需要一个音频长度统计程序，将计算好的音频长度写入数据库

### 解决思路

1. **字段结构（一一匹配怎么落）**：现有 `audio_versions`（版本名 → 本地路径）与 `audio_version_list`
   （版本名列表）是「同一批键，两种视图」。新字段 `audio_durations` 采用 **JSON：版本名 → 秒**
   （`{"鋼琴版": 144.171, "人聲版": 167.163}`），键集严格等于 `audio_versions` 的真实版本键
   （剔 `_` 前缀元信息键，用 `naming.is_audio_version_key`）——读不出时长的版本**键仍保留、值落 `null`**，
   这样「三列键集一致」可用一条 SQL / 一个统计函数直接校验，不会因个别文件缺失而塌缩。
2. **时长怎么读（两个候选，实测选优）**：
   - `ffprobe` 不存在（无 ffmpeg）；自写 MP4/MEPG 解析可行但要自己处理 VBR/Xing/坏帧，维护成本高。
   - 选 **mutagen**（新增依赖，`config/requirements.txt`）；关键实测结论：`mutagen.File()` 靠
     **类型嗅探** 选实现，对本库 3 个**无 ID3 标签**的 MP3（#138 / #197 / #296_b 人聲版）返回 None；
     改为**按后缀显式分派** `mutagen.mp3.MP3` / `mutagen.mp4.MP4` 后 **1119/1119 全部读出**
     （27.2–389.2 秒，中位 154.5）。故 `crawler_core/audio_duration.py` 用后缀分派，未知后缀才回落 `File()`。
   - 另外 3 个 m4a（#3 四部合唱版、#473/#474 鋼琴版）的自写 mvhd 扫描读不出（moov 在 mdat 之后且 box 处理有坑），
     mutagen 的 `MP4`（优先进音频轨 `mdhd`）全部正常——这也是不自己造轮子的直接理由。
3. **列顺序**：沿用项目既有机制——**代码 DDL 才是唯一权威**。把新列写进 `_create_table_v4`
   （紧跟 `audio_version_list`，在 `api_raw` 之前），再跑 `tool/reorder_table_columns.py` 事务重建表
   对齐物理列序（v5~v7 都是 `ALTER` 追加、必然错位，这次不再让 DB 落后）。
4. **谁能写这一列**：`audio_durations` **只由统计工具写**。`save_to_db`（Step 2 / 增量同步）与
   `downloader` 的路径回写都不碰它，避免爬取流程重跑时把已算好的时长清空；`save_to_db` 里也
   幂等 `ensure_audio_durations_field`（只补列、不改值）。
5. **工具形态**：`tool/build_audio_durations.py`，选项风格对齐 `tool/build_score.py`
   （`--only/--limit/--db/--dry-run/--stats/--show/--quiet`），批量统计里单个坏文件只记 `null` + 原因、
   不中断整批；默认幂等（JSON 未变的行不计入“更新”）。
6. **测试**：不引入外部音频素材——**合成** 100 帧 MPEG1 Layer3 CBR（2.61 s）与最小 MP4
   （`ftyp + moov[mvhd, trak[mdia[hdlr('soun'), mdhd]]]`，含「无 soun 轨回落 mvhd」两条路径）
   做真文件读取断言；工具逻辑用临时库 + 合成文件覆盖（键集一一匹配 / 幂等 / dry-run / 坏文件 / 子集选择）。
