## 任务 2：把 `tjc_hymn` 表的列顺序调整为 `_create_table_v4` 的顺序

### 提问
2. 调整数据库 `tjc_hymn.db` 的 `tjc_hymn` 表的列顺序，**按照 `crawler_core/db.py` 代码中 `_create_table_v4` 函数创建表的顺序**调整。

### 解决思路
- **现状诊断**：`PRAGMA table_info(tjc_hymn)` 显示列尾为
  `… audio_versions, updated_at, audio_version_list, staff_png_path, numbered_png_path, download_status, integrity_status, chorus, api_raw`
  —— 原因清楚：v5（PNG 路径）/v6（`chorus`）/v7（`api_raw`）都是 `ALTER TABLE ADD COLUMN` 追加，SQLite 只能挂到末尾；
  而代码 `_create_table_v4`（用户已把 `api_raw` 上移到 `download_status` 之前）的顺序才是权威。
- **方案对比**：
  ① 在 SQL 里手写目标列清单重建 —— 与代码脱钩，代码再改 DDL 又会对不上；
  ② **解析 `db.py` 源码里的建表 SQL 作为唯一权威**（正则取出 `_create_table_v4` 的 DDL → 逐行提列名 + 原样复用 DDL 建临时表），
  事务内 `建临时表 → INSERT ... SELECT（显式列名）→ DROP → RENAME` —— 选 ②，并落成可重复执行的
  `tool/reorder_table_columns.py`（幂等 + `--dry-run` + 重建后自检），以后库/代码不一致随时一条命令对齐；
  ③ `PRAGMA writable_schema` 直接改 `sqlite_master` —— 绕过校验、风险高，弃。
- **必须保住的细节**：`id` 值（1–474）、`UNIQUE(hymn_number)`、`sqlite_sequence`（真实库为 **949**，远大于最大 id 474，
  不显式还原会让后续 id 分配悄然回退）、`hymn_category`（47 行）不受影响；全过程放进事务 + 事前备份 + 事后逐行逐列比对。

### 最终结果
- **改了什么**

## 会话总结

- 本次共处理 **2** 个任务
- 关键收获：
  1. 结构性诉求（"列顺序要跟代码一致"）最稳的落法是**把代码 DDL 当唯一权威 + 工具自动对齐**，人工清单必然腐化；
  2. 物理重建表必须**显式还原 `sqlite_sequence`**（AUTOINCREMENT 计数），否则 id 分配会静默回退；
  3. 资源替换后要看 **mtime/内容对照**判断图片是否真的重画（本次旧 PNG 早于新 PDF 就是线索），重画后**人工读图**复验最直接；
  4. `rebuild_all()` 这类"扫全目录"的工具要显式处理"无可登记文件"的目录，否则会产生 `[]` 噪音清单；
  5. 工具经验：`replace_in_file` 的 `old_text` **首行不能带缩进**（否则报 text not found），从行首字符（如 `-`/`>`/`|`/标题）开始写即可；
     pyright CLI 必须 `--pythonpath` 指向项目解释器，否则 selenium/PIL 会被误报成 `reportMissingImports`（19 条假告警）。
- 环境观察：`data/赞美诗PPT/`（用户 19:45 放入，123 MB / `.ppt`）已加入 `.gitignore`，避免误提交
- 遗留事项：无（`tool/bench_api.py`、`selenium_legacy` 的 `-m selenium` 用例、204 首副歌的 PDF/OCR 补全路线仍属 P3 可选增强）。
