## 任务 3：把 PPT 里的「带简谱文字歌词」论证并落库

### 提问

1. 现有 DB 与原始资料里，歌词有纯文字版，简谱/五线谱的**曲谱信息只在 PDF→PNG 图片里**，文字歌词没有曲谱；
2. `data/赞美诗PPT/`（474 份 PPT）每首对应一份，内容是**加了简谱的文字歌词**，但本机没装
   `data/赞美诗PPT/简谱字体/` 里的字体，所以肉眼看不见；用户判断"可以通过匹配规则，从字体库里在 PPT 中找到对应关系"；
3. 需求：**在 `tjc_hymn.db` 中增加带简谱的文字歌词**，动手前先论证三件事：
  ① 存 DB 是否可行（不行的话哪种格式合适）；② 新建表还是扩充 `tjc_hymn`；
   ③ 怎么保证曲谱与歌词的**等长匹配**、防止对不上导致唱错；
4. 论证没问题就选最佳方案执行。

### 解决思路

**一、先取证（不猜，全部落到可复现的证据上）**

- 环境：无 Office/LibreOffice，`.ppt` 是二进制 OLE/CFB → 用 `olefile` + 自写记录流遍历器
  （`[MS-PPT]` 8 字节记录头，`) recVer==0xF` 为容器）读 `PowerPoint Document` 流的
  `TextCharsAtom/TextBytesAtom`，并以 `TextHeaderAtom` 区分母版/页标题/正文（正文=角色 5）。
- 结构：**每张幻灯片 = 一节**；正文以 `\r` 分行：标题行 →（可选）节标签 `(副歌)`/`(三)` →
  「简谱记号行 + 歌词行」若干对 → 节号 `k/M`。（样本 `001.ppt`、`002/005/006.ppt`、
  `349/354.ppt` 逐一打印原文确认，含 349 节号后孤立 `。`、354 每页 `(副歌)` 标签、023 标签粘在标题行尾等畸形）
- 字体：`简谱字体.ttf` = 01SMN "Simple music notation"（95 个码位，ASCII 全覆盖）；
  `歌词字体.ttf` = DFKai-SB（upm 1024，汉字 1em / ASCII 0.5em）。
- **记号语义**（关键）：PPT 文本本身是**纯 ASCII**，字体只是渲染层。把每个码位**落图**
  （PIL 渲染 + 基线/em 参考线）后与官方简谱 PNG 逐音比对，确认：
  `1-7` = 音级；`q w e t y r u`（全宽）/`a d f g h j s`（半宽）= 「数字+减时线」合成字形；
  `Q W E R T Y U`、`! # $ @` = 带高八度点；`` ` `` = 休止符 `0̲`；`/` = **延长线**（`1//` ≙ 官方 `1 - -`）；
  `\` = 小节线、`|` = 终止线；`0 8 9 = - i k P p o` 等（adv=0）= 附点/八度点/升号等**零宽叠加修饰**。
  验证样例：#5 第 1 行 `qw \ 3 5 3 2 \ 1//` 渲染出 `1̲2̲ | 3 5 3 2 | 1 - -`，与官方简谱旋律逐音一致；
  #13 第 1 行 `3 e . s 1 q . jk \ 68 1 yi ti ` \` 渲染出 `3 3̲.2̲ 1 1̲.7̲ | 6 1 6̲5̲0̲ |` 与官方完全一致。

**二、三个问题的结论**

1. **可行性**：可行，且**存文本**（原始 ASCII 记号串）最优——它是纯 ASCII、可解析、可校验、可无损渲染；
   存图片/PDF 只是重复既有 PNG、JSON 大字段又无法在 SQL 层做校验，都不如"记号+歌词两行原样存"。
2. **表设计**：**新建两表**（不改 `tjc_hymn`）。理由：一首诗是「节 × 行」两级且行数不定（1:N），
   宽表只能再 `ALTER TABLE ADD COLUMN`（重演 v5~v7 列序错位）或塞 JSON；独立两表还能容纳
   **甲/乙版本**（DB 编号 `51_a`/`51_b`）并让"行级异常"可直接 SQL 查。
3. **等长/防错配**：PPT 的两行是作者**手工用空格+字号对齐**的，**逐字对位没有严格数据保证**——
   这点必须诚实说明。因此采取"原样保存 + 5 项可验证校验 + 人工终审出图"：
   ① 行级配对（简谱行必须紧跟歌词行）；② 节号 `k/M` 与张数自洽；③ **跨节曲调一致**（旋律签名比对）；
   ④ **歌词归属**（与 DB 正歌/副歌逐字覆盖率 ≥0.75，反查编号）；⑤ 音符数 ≥ 字数（`count_delta`，<0 必须复核）。

**三、若干坑与决策（都是实测踩出来的）**

- PPT 文件名编号是**旧版编号**（`349.ppt` 是"救主正在等待"，而 DB #349 已是"奇妙的耶穌"）
  → 编号只能靠**标题匹配**（繁简归一 + 异体字折叠 `爲→為`）+ 标题模糊时用**歌词反查**兜底；
- DB 标题带 `(甲)/(乙)` 后缀且编号为 `51_a/51_b` → 标题匹配必须**按版本消歧**，否则甲乙串号；
- 半宽字母（`s`=2̲、`j`=7̲）也是音符——最初漏了它们，导致 2531 行误报"音符不足"（修后降到 20 行）；
- 曲调周期 P：`#5` 一类诗"一节正歌分两个半段"（P=2，幻灯片数=节数×2），用旋律签名推周期；
- `tune_period` 的 `p == len(sigs)` 会让 `all()` 空真判真 → 把 429 首都伪装成"同调"，
  修掉后**真实检出 41 首**作者记谱手误（如 `q5812` 写成 `15812`、末小节多写 `\`）；
- 标签行可能带前导空格/粘在标题行尾/夹在行对之间 → `LABEL_RE` 加 `^\s*`、加 `LABEL_TAIL_RE`、循环内识别；
- 主键定为 `ppt_file`（474 份 PPT 是数据主体），`hymn_number` 降为关联列（未匹配留空，不丢数据）。

## 任务 4：论证「以官方简谱 PDF 为辅，做曲谱-歌词等长对位」的可行性

### 提问
Q3 怎么保证等长匹配？能否通过读取 PDF 内容来定位曲谱与文本的匹配问题，
甚至实现「以 PPT 为主、简谱歌词 PDF 为辅」的曲谱文本与歌词文本等长匹配？

### 解决思路
先取证再下结论——唯一的分歧点是：**官方简谱 PDF 里到底是「文本+坐标」还是「扫描图片」**。
- 双路取证：系统 poppler（`pdfinfo`/`pdffonts`/`pdfimages`/`pdftotext`）+ PyMuPDF（字符级 bbox/font/gid）
- 实测结论：PDF 是 **iTextSharp 4.1.6 生成的矢量 PDF**（2022-06-10），
  音符 = `MMP2005` 字体**文本**（28pt），歌词 = 中文字体**文本**（14pt），
  全部「图片」都是 1×1 / 10×1 的排版微图（共 2132 个），**没有扫描页**，
  矢量 path 数为 0 → 即 PDF 给出的是**几何真相**：每个音符、每个字都有精确坐标
- 因此方案不是「OCR 认图」，而是**直接读坐标做对位**，可靠性远高于 PPT 侧的手工空格

### 最终结果（证据）
- **字体结构**：`ABCDEE+MMP2005`（Mumin Music 2005 官方简谱字体，unitsPerEm=2048，post 3.0 无 glyph 名，
  cmap 含 110 个 CJK 码位映射）；音符字符编码是**字体私有 CJK 码位**
  （如 `U+3021 〡` / `U+4E52 乒` / `U+602D 怭`…#1 实测用到 33 个码位）
- **坐标对位实测**（#1 第 1 乐句）：歌词 15 字的 x 与音符网格 x **15/15 全部重合（Δ≤3pt）**——
  `聖97 哉118 ，125 聖139 哉160 ，167 聖204 哉253 ，260 全315 能354 大364 主426 宰465 ！493`；
  另用 PyMuPDF 渲染整页（200dpi）+ PIL 画点叠图复核：**红点全部落在官方简谱音符上**

## 会话总结

- 本次共处理 **4** 个任务
- 关键收获：
  1. 结构性诉求（"列顺序要跟代码一致"）最稳的落法是**把代码 DDL 当唯一权威 + 工具自动对齐**，人工清单必然腐化；
  2. 物理重建表必须**显式还原 `sqlite_sequence`**（AUTOINCREMENT 计数），否则 id 分配会静默回退；
  3. 资源替换后要看 **mtime/内容对照**判断图片是否真的重画（本次旧 PNG 早于新 PDF 就是线索），重画后**人工读图**复验最直接；
  4. `rebuild_all()` 这类"扫全目录"的工具要显式处理"无可登记文件"的目录，否则会产生 `[]` 噪音清单；
  5. 工具经验：`replace_in_file` 的 `old_text` **首行不能带缩进**（否则报 text not found），从行首字符（如 `-`/`>`/`|`/标题）开始写即可；
     pyright CLI 必须 `--pythonpath` 指向项目解释器，否则 selenium/PIL 会被误报成 `reportMissingImports`（19 条假告警）。
  6. **二进制格式取证要"落到图片上"**：PPT 记号语义靠"字体落图 + 官方简谱 PNG 对照"才敲定，
     纯代码推断（如按 advance 猜语义）会把半宽合成字形、零宽修饰判错，直接导致 2531 行误报；
  7. **校验逻辑警惕"空集合真"**：`all(... for i in range(0))` 恒真，会让跨节曲调一致性校验静默失效（429 首伪装通过）；
     修掉后真实检出 41 首记谱手误——**校验器本身也要被测试覆盖**；
  8. **源数据的"不确定性"要显式建模**：旧版/新版编号、甲/乙版本、标签写法、手工对位的不确定性，
     都应变成可查询的列（`title_match`/`version`/`label`/`count_delta`/`align_ok`）而不是在代码里"猜一个答案"。
  9. **「能不能」要靠一手取证回答**：PDF 能否做对位的分水岭是「文本层 vs 扫描图」——
     `pdffonts`/`pdfimages`/`pdfinfo` 三条命令即可定性（本次是 iTextSharp 矢量 PDF + 嵌入 MMP2005），
     再用 PyMuPDF 取字符级 bbox，最后**叠图目视**确认坐标落点，比任何推断都可靠；
  10. **对位基准要选「权威且带几何」的源**：PPT 的作者手工空格是「人肉排版意图」，PDF 的字符坐标是「排版机几何真相」，
     后者可给出 Δ≤3pt 的置信度；但两者**用途不同**——PPT 给音级语义（已人工确认），PDF 给位置与计数，互证才完整；
  11. **换源要先查结构同构性**：全量普查 474 份 PDF 得 473/474 同构（393 份 1 页 / 80 份 2 页），
     唯一例外 `#349` 无 MMP2005 无中文 → 方案必须先做「普查再分治」，否则会在个别文件上静默出错；
  12. **多声部是易踩的坑**：官方 PDF 是四声部合唱谱，PPT 只有主旋律，「选错声部」会让对位整体偏移，
     所以自动选声部（与 PPT 音级序列匹配度最高者）应作为对位的前提步骤。
