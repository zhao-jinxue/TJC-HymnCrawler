# PPT + PDF + PNG 三源综合方案可行性调研

- 日期：2026-09-15
- 工具链：Cline
- 涉及模块：`crawler_core/pdf_jianpu.py`（既有 POC）、`Hymn_Downloads/`（官方 PDF/PNG）、`data/赞美诗PPT/`（PPT 源）、`tool/qwen_ocr.py`（视觉模型通道）

## 背景

上一次会话（`docs/sessions/2026-09-13_19-18-00.md`）已完成「PPT 记谱 × 官方简谱 PDF」逐字几何对位 POC，并明确其硬边界是**粒度不可比**（PPT 合成字形 1 字符/拍 vs PDF 把减时线/附点拆成独立字符）。

本次用户提问：**PPT + PDF + PNG 三源综合（PDF 为主、PPT 为辅、难抉择时用图片识别）这个套路是否可行？**

回答该问题必须先确定三件事实，本任务即围绕取证展开（**只读探查 + 视觉 API 实测，未改动业务代码**）。

## 任务 1：三源是否互相独立 + 图片识别通道能否胜任裁决

### 提问

> 那么 PPT + PDF + PNG 三个元素综合呢，以 PDF 为主，PPT 为辅，难以抉择的使用图片识别，这个套路是否可行？

### 解决思路

把「三源综合」拆成三个必须单独证伪的问题，逐个做实测而不是凭直觉判断：

1. **PNG 是不是独立第三源？** 若 PNG 只是 PDF 的位图版，则「三源」实为「两源 + 一个渲染通道」，架构上不该按三个源来设计。
   判据：把官方 PDF 用 pymupdf 渲染成图，与官方 PNG 对齐后比内容区比例、墨迹占比、像素相关系数。
2. **「图片识别」通道的必要规模？** 若绝大多数 PDF 自带文本层，则 OCR 只是例外通道，而非常规路径。
   判据：统计 474 首官方简谱 PDF 的文本层字符数分布与页面内嵌图片数。
3. **视觉模型能否胜任「难抉择时的裁决」？** 要看它在**本项目真正需要的能力**（读八度点、逐字对位）上的表现，且要分清「模型不会读」与「输入方式不对」。
   判据：用同一张官方简谱图做三组对比实验——整块输入、单行裁图输入、单行裁图 + 明确简谱规则提示。

### 最终结果

#### 事实 1：PNG 不是独立源，它是 PDF 的位图孪生（三源 → 实为两源）

`Hymn_Downloads/<编号_标题>/` 下每首 4 个文件：`*_简谱.pdf` / `*_简谱.png` / `*_五线谱.pdf` / `*_五线谱.png`（474 首 × 2 版式 = 948 PDF / 948 PNG）。

对 #1 的比对（脚本 `/tmp/probe_pdf.py`）：

| 指标 | 官方 PNG | 官方 PDF @240dpi 渲染 |
| --- | --- | --- |
| 页面/图幅比例 | 0.6559（1984×3025） | 0.7070（A4 595×842pt）→ 渲染 1985×2807 |
| **裁白边后内容区比例** | **0.6466**（1905×2946） | **0.6463**（1524×2358） |
| 墨迹占比（<128 灰阶） | **0.0556** | **0.0556** |
| 内容区对齐后相关系数 | — | 0.8457（上部 1/3 为 0.8117，差异仅来自抗锯齿） |

并排目视（`/tmp/cmp_top.png`）：左 PNG / 右 PDF 渲染**逐像素同排版**，标题、调号、四声部、歌词完全一致。

→ 官方 PNG = 官方 PDF 去掉 A4 白边的高清位图。**用 PNG 与用 PDF 渲染得到的是同一信息**，不构成独立第三源。

#### 事实 2：474 首简谱 PDF 全部带文本层，「图片识别」只是例外通道

统计结果（脚本 `/tmp/probe_pdf_text.py`）：

```
简谱 PDF 总数: 474
文本层分布: {'无文本(<10)': 0, '极少(10-200)': 0, '中等(200-2000)': 401, '丰富(>2000)': 73}
页面内嵌图片对象累计: 14331   （≈30 个/页）
```

→ 没有一首是「整页图片版」。#349 的问题不是缺文本层，而是其它结构差异（需另行排查）。
→ 页面内嵌的 14331 个图片对象印证了既有结论：**小节线、延音弧等装饰是图片，不在文本层**，这才是几何对位需要图形判据的原因。

#### 事实 3：视觉模型「读单行可靠、对位不可靠」，且模型选择有硬差异

三组实验（同一首 #1 官方简谱 PNG，Qwen-VL，`temperature=0.1`）：

| 实验 | 输入 | 模型 | 结果 |
| --- | --- | --- | --- |
| A | 整块（含双声部 + 3 段歌词，1905×900 原分辨率） | `qwen-vl-max` | 8 小节音符数字**读对**；但**低八度点系统性丢失**（`6̣`→`6`、`4̣`→`4`），**逐字对位大面积 `?` 且错位**（把下一乐段歌词算进本节） |
| A | 同上 | `qwen-vl-ocr` | 输出 JSON 但文字块切分错乱（漏字），音符仅按空白切分，**无用** |
| B | **单行裁图**（低音声部一行，2× 放大） | `qwen-vl-max` | `1 1 6. 6. \| 5. - 1 - \| 4. - 4 4 \| 1 -` — **与目视真值逐字一致，八度点全对** |
| B | 同上 | `qwen-vl-ocr` | `11665-1-4-441-` — 丢失小节线与间隔，**无用** |

（实验 A 中同图残留的半个上行被读错，属输入残缺，不计入模型能力评价。）

→ 结论：**`qwen-vl-max` 是「逐行读数器」而不是「对位器」；`qwen-vl-ocr` 完全不适用于简谱。**
→ 扬长避短的用法：**由程序按行切片（PDF 文本层的行 bbox 天然给出切片范围）→ 模型只读单行 → 仍由程序做逐字对位**。这是可行且低成本的例外通道。

### 综合结论（回答用户提问）

| 原方案设定 | 取证结论 | 修订建议 |
| --- | --- | --- |
| PDF 为主 | ✅ 成立，且 PDF 同时提供「文本层 + 可渲染像素」两条通道 | 保持主线：`pdf_jianpu` 几何对位 |
| PPT 为辅 | ✅ 成立，但粒度不可比，宜作**候选真值/投票源**而非对位源 | 先做拍位聚合/粒度归一，再用于交叉校验 |
| PNG 作第三源 | ❌ 不成立：PNG 是 PDF 的位图孪生，无新信息 | 不算第三源；需要像素时现场渲染 PDF 即可 |
| 难抉择时用图片识别 | ⚠️ 部分可行：仅作**逐行读数裁决**（qwen-vl-max），**不能**做对位裁决 | 例外通道：按行切片 → 单行读数 → 程序对位；只用于几何对位失败的争议行 |
| （原方案遗漏） | — | 若要真正的独立第三源，应是**五线谱**（另一记谱体系，474 首齐备），但需五线谱识谱，成本另计 |

### 遗留问题

1. 事实 2 显示 #349 **并非**无文本层 → 上次会话把它归为「疑似图片版」的判断需要修正，应重新排查其真实失败原因。
2. 「拍位聚合/粒度归一」仍未实现，是全量命中最关键的一步。
3. 视觉裁决通道若要落地，需新增按行切片工具（`tool/show_pdf_align.py` 已有行 bbox 与渲染能力，可复用）与单行读数结果与 PPT 行的序列比对逻辑。
4. 真正的第三独立源（五线谱）可行性未评估。

## 任务 2：L2（拍位聚合/粒度归一）与 L3（跨源交叉校验）能否组合

### 提问

> L2 和 L3 方式，可以组合吗？

### 解决思路

组合问题不能只凭架构直觉回答，先做取证：**把「粒度不可比」的真实成因找出来**，才能判断两个环节的接口能否共用同一数据结构、能否互相回灌。为此连续做了四个探针：

1. 修饰字符的形态聚类（`(iw, ih)` 四元组能否分类）→ 判断「拍单元 = 主字形 + 修饰槽」是否成立；
2. PDF 元素数 vs DB 记号数逐首比对 → 定位粒度差的具体数量来源；
3. PDF 元素序列与 DB 记号原文逐位并排 → 看差异出现的具体位置；
4. 渲染官方谱那一行的图像目视 → 确定官方版的记谱单位（几小节几拍）。

### 最终结果

#### 实测 A：修饰字符形态可分类，但 `is_dot` 判据有漏网

`#1/#5/#13/#334` 共 275+ 个非主层字符的 `(iw, ih)` 聚类：

| 形态（iw×ih，em） | 含义 | 数量 | 现状 |
| --- | --- | --- | --- |
| 0.14~0.27 × 0.33~0.50 | 音符/休止/合成字形 | 大量 | ✅ 保留为元素 |
| 0.21 × 0.046 | 延长线 `-` | 16 | ✅ 保留（占时值，正确） |
| 0.26 × 0.020 | 半宽减时线 | 6 | ✅ 被 `is_dot` 剔除 |
| **0.93 × 0.111** | **全宽减时线/连音线** | 4（#1）、4（#20） | ❌ **漏剔！**（`DOT_MAX_H=0.10` < 0.111 → 被当成时值元素） |
| 0.034~0.23 × 1.12~1.16 | 小节线/括弧 | 121+24 | ⚠️ `melody_rows` 会把它自成的"行"当谱行 |
| 0.00 × 0.000 | 空白占位 | 275 | ✅ 已剔 |

→ 结论：`(iw, ih)` 足以把字符分成「音符 / 延长线 / 小标记 / 线类 / 空白」五类，**但必须用「音符形态白名单」而不是当前的「黑名单式 `is_dot`」**。

#### 实测 B：`melody_rows` 的行识别把噪声层当谱行

- `#5`：32 条"旋律行"里有 8 条是 `602d 602d 602d 602d`（**四根小节线自成一 y 层**，恰好满足 `min_elems=4`）；
- `#20`：33 条里同类噪声更多；`#5` 行 9 的元素是 `(0.67×0.092)×4`（装饰层）；
- `#1`：16 行元素数整齐（16），与 DB 的 16 一致 → 这才是能命中的样本。

#### 实测 C：粒度差的真实成因不是"减时线拆字符"，而是**合成字形的拆分方式不同**

渲染 `#334`（旧版 329）官方谱第 1 行目视：

```
S 声部:  1 - 1. 2 | 3 - - 4 | 3 1 1 7 | 1 - - 0
A 声部:  5 - 6. 7 | 1 - - 1 | 1 1 5 5 | 5 - - 0
歌词  :  ①天 父 我 神， 用 大 權 能 聖 手，
```

对应 PDF 字符（y=172.8 层，cx 列完全固定）：

```
cx: 103 124 144 180 219 240 261 282 330 351 372 397 441 462 483 504
cp: 4e52 5d1f 4e52 4ee5 4e56 5d1f 5d1f 4e58 4e56 4e52 4e52 4e4f 4e52 5d1f 5d1f 5d4c
    1    -    1    1.   3    -    -    4    3    1    1    7    1    -    -    0
```

关键发现：

1. **官方谱一行 = 4 小节 × 4 拍位**，每拍位一个字符槽；
2. **`1.`（数字+附点）在 PDF 里是单个合成字形**（码位 `4ee5`），而 PPT 是「数字 + 零宽附点」两个字符 → **这才是"粒度不可比"的真实来源**（此前以为是减时线被拆）；
3. **x 间距携带时值**：21pt/拍；`1.` 与 `2` 相距 36pt（附点时长），故「拍位」可由 x 栅格换算；
4. `#13` 的 PDF 19 元素 = DB 的 `11 + 8`（s1l1+s1l2）→ 是**行-节映射**差异，不是粒度问题；
5. `#334` 的 PPT 记谱（`3.w q w 3 5 /`）与官方谱（`1 - 1. 2`）旋律明显不同 → **不同版本/声部**，这类样本应以"拍数守恒失败"进入争议清单，而非当作错误。

#### 综合结论：**可以组合，而且必须组合——两者的接口是同一个「拍单元」**

| | 单独做的问题 | 组合后的分工 |
| --- | --- | --- |
| L2 拍位聚合 | 能把 PDF 元素投到拍栅格，但**不知道 PPT 合成字形（`w/q/t/y`）的时值语义** → 算不出 PPT 侧拍数，归一后无法比较 | 提供**坐标系**：拍位栅格 + 每拍的（主字形，修饰/时值）槽位 |
| L3 交叉校验 | 字符级投票在合成字形处必然冲突（现有 `learn_across` 的 `conflicts` 机制正是在剔除这些码位）→ 映射覆盖不到 `w/q/t`，40 首只命中 9 首 | 提供**语义**：学习「(主码位, 时值/修饰类) ↔ PPT 记号」的投票键，累计票数与冲突 |

组合形态（反馈环，现有 `learn_across` 已是雏形，只是坐标系粒度错了）：

```
种子映射（严格匹配挖出）
   → L2 归一：PDF 行 → 拍序列；PPT 行 → 拍序列（时值表由 L3 提供）
   → L3 按【拍单元】投票（不再是字符级），冲突票 = 争议定位
   → 新映射回灌 L2 的 PPT 时值表 → 下一轮对齐更多行（正反馈）
   → 硬约束：拍数守恒（PDF 拍数 == PPT 拍数）抑制假匹配
   → 争议清单（拍级定位）→ L4 视觉裁决 / 人工
```

三项额外收益：① 命中率上限从"整行同构"提升到"拍级可比"；② 冲突可定位到具体拍（可解释、可复核）；③ 版次差异/手误自动落入争议清单，不再污染映射学习。

#### 组合前提（必须先把这 4 个判据问题修掉）

1. `melody_rows` 行识别改「音符形态白名单 + 剔除线类层（ih>0.8）与元素数<4 的装饰层」；
2. 幽灵元素过滤（`iw > 0.5` 的全宽减时线/连音线）；
3. 拍位栅格化（21pt 基准，行首元素定起点）+ 时值由相邻元素 x 差估计；
4. PPT 合成字形时值表（`w/q/t/y/adf...` 逐字符几何反推，474 首全量统计可穷举验证）。

### 遗留问题

- 上述 4 项判据修复尚未实现（本轮仍为只读探针）；
- `#334` 一类"版本/声部差异"样本的判定规则待定（拍数守恒失败 → 争议 vs 直接排除）；
- `#349` 仍缺 PDF/DB 记录（探针显示"缺 PDF 或 DB 记录"），需单独排查。

## 会话总结

- 本次共处理 2 个任务（三源可行性取证 + L2/L3 组合可行性），**未改动业务代码**，仅新增本会话日志。
- 关键收获：
  1. 「多源」必须先用**量化判据**验证源的独立性——本项目里 PNG 与 PDF 内容区比例 0.6466 vs 0.6463、墨迹占比完全相同，实为同一信息的两种编码；
  2. 视觉模型的能力边界要按**任务动作**切分验证：`qwen-vl-max` 读单行简谱（含八度点）完全正确，但整块对位与八度判定崩坏；`qwen-vl-ocr` 对乐谱语法完全不可用；
  3. 474/474 首 PDF 均有文本层 → 图片识别应定位为**例外裁决通道**，而非常规流水线环节。
- 关键收获（任务 2，L2/L3 组合可行性）：
  1. 「粒度不可比」的真实成因是**合成字形的拆分方式不同**——官方 PDF 把「数字+附点」做成单字符（`1.`=`4ee5`），PPT 拆成「数字 + 零宽附点」；此前归因于"减时线被拆"并不准确；
  2. 官方谱一行 = **4 小节 × 4 拍位**、x 间距 21pt/拍 → 「拍位栅格」是把两侧拉到同一坐标系的正确单位；
  3. L2 与 L3 **接口同构、互为闭包**：L2 给坐标系、L3 给语义（合成字形时值），分开做都不成立，合起来才闭环；
  4. 顺带发现 4 个必须修的判据问题：`melody_rows` 把小节线层/装饰层当谱行、`is_dot` 漏剔全宽减时线（`0.93×0.111`）、拍位未利用 x 时值、PPT 合成字形时值语义未建表。
- 遗留事项：先修上述 4 项判据 → 拍级投票反馈环（L2+L3 组合）→ 争议清单接 L4 视觉裁决 → 五线谱源评估 → 全量表结构设计，均待用户决定是否启动。
